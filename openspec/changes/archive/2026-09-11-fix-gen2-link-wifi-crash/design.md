## Context

The Game Boy Link protocol uses an external ~8 kHz serial clock generated by the Game Boy. The ESP32-S3 uses a GPIO change interrupt (`GBLinkDriver::isrHandler`) on GPIO 4 to service every bit (falling edge puts out data, rising edge reads data). 

Previously, upon completing an 8-bit byte exchange, the ISR called `onByteExchange()`, which directly invoked `updateStatus()`. This immediately triggered WebSocket text broadcasts (`_ws.textAll()`), JSON serialization, and dynamic heap memory allocations (`malloc`) inside the hardware interrupt service routine. In FreeRTOS / ESP-IDF, calling `malloc` or network mutexes from an ISR triggers a fatal kernel panic (`!xPortInIsrContext()`), resetting the CPU and tearing down the Wi-Fi AP. Additionally, Gen II games transmit larger blocks (441 bytes vs 415 bytes in Gen I, plus 389 bytes of Mail data), causing buffer overruns if default Gen I configuration is active.

## Goals / Non-Goals

**Goals:**
- Completely decouple the hardware interrupt from network and memory allocation tasks.
- Keep the ISR execution time under 2 microseconds so clock pulses are never missed.
- Auto-detect Gen I (`0x60`) vs Gen II (`0x61`) in the initial handshake and automatically reallocate buffers and notify the web UI.
- Ensure all functions in the link ISR execution chain have `IRAM_ATTR` to prevent cache-disabled panics during Wi-Fi transmissions.
- Maintain a rock-solid Wi-Fi connection while a Game Boy Color running Pokémon Gold is actively trading.

**Non-Goals:**
- Rewriting the core Pokémon trade state machine or altering the byte sequence of the original Game Boy trade protocol.
- Emulating wireless adapters or Gen III games.

## Decisions

### Decision 1: Atomic Status Flags and Task-Context `process()` Dispatcher
- **Chosen Option:** The ISR in `onByteExchange()` only sets volatile primitive flags (`_status_pending = true`, `_pending_status = new_status`, `_pending_msg = msg`). The main FreeRTOS task loop (`loop()`) calls `TradeEngine.process()`, which checks the flag and safely invokes `_event_cb()` and `WebManager.broadcastStatus()`.
- **Rationale:** Standard embedded systems best practice. ISR stays ultra-fast and deterministic (< 1 µs), with zero `malloc` or FreeRTOS mutex conflicts.

### Decision 2: Automatic Generation Detection during Handshake
- **Chosen Option:** In `handleConnectPhase()`, if `in_byte == 0x61`, the system detects a Gen II game; if `in_byte == 0x60`, it detects Gen I. A pending generation switch flag (`_pending_gen_switch`) is set.
- **Rationale:** The user no longer has to remember to change the dropdown before plugging in the cable. When `process()` runs, it safely reallocates the 441-byte Gen II buffers and broadcasts a `generation` event to the web UI.

### Decision 3: IRAM Placement for Link Chain
- **Chosen Option:** Decorate `driver_callback_shim`, `onByteExchange`, `handleConnectPhase`, `handleMenuPhase`, `handleTradeCentrePhase`, and `plist_index_get` with `IRAM_ATTR`.
- **Rationale:** Prevents `Cache disabled panic` when interrupts arrive during Wi-Fi flash cache operations.

### Decision 4: Deferring `rebuildPatchList()` to Task Context
- **Chosen Option:** In `STATE_TRADE_DONE`, flag `_rebuild_patch_pending = true` instead of calling `rebuildPatchList()` directly in the ISR.
- **Rationale:** `rebuildPatchList()` frees and allocates memory via `malloc()`. Executing it in `process()` guarantees ISR safety.

## Risks / Trade-offs

- **[Visual update latency]** → Decoupling to `loop()` introduces up to 5-10 ms latency before the WebSocket message is sent. This is completely imperceptible to humans and eliminates the crash.
